## 2. Shared construction and assertions

Use disposable migrated SQLite at head `0008`, synthetic data, an active stored doctor and session assigned to the patient, pinned `2026-11-14T12:00:00Z`, and `tmp_path` source bytes with matching size and SHA. Stage synthetic facts and scripted doctor decisions honestly; these are not extracted PDFs, real source-image review or clinician interactions. F0 `create_run_foundation` requires at least one selected, preflight-clear document; record the real queued run, selected document/observation manifests and any omission evidence, not fabricated IDs. F1 `evaluate_run_verification_gate` commits an actual decision and `workflow.gate.evaluated` audit; a matching current PROCEED with no blockers is necessary for F2/RB1 and RB3. Use fresh clean sessions as required; F2 and RB1 are read-only and recheck F1. F2 compares up to 365 days; RB1/RB2 use 90 days. RB3 owns its write transaction and revalidates, including selected bytes. DB locks do not make filesystem bytes atomic: the documented post-T17 race remains.

The RB3 policy reference is `demo-policy-1.1.0`, canonical SHA `f3bdad3f6a958b65b50598910cc91501dcc53ca210ff90d2e09b14695cb6bd36`; parameters are arbitrary demo inputs, not clinical guidance or runtime policy approval. RB2 sorts by hint (`verification_needed`, `data_quality`, `change_to_review`), rule ID and evidence/dedupe; evidence-derived dedupe happens before a fail-closed cap of 3 per measure type. A selected current set is explicit; history alone does not trigger rules. Output `provenance_status=fixture_asserted` is RB3's owner-ratified A2 **transport label**, not human assurance. `stored_lineage_proved=1` only when every linked observation has independently proved verified-document lineage; self-reported links yield 0. Review items are open, demo-only, with observation links only; no document-span links are permitted.

For every authorized success below, assert exactly one `review_evaluation` per run and one associated `workflow.review.persisted` audit event, matching actor/patient/run/subject/outcome and bounded nine-key safe detail, gate ID/fingerprint, bridge fingerprint, RB3 input/output fingerprints, pinned policy and counts. First receipt says completed, `replayed=false`, and per-call writes equal totals. Repeat with identical current evidence: same evaluation/audit/item/link identities and fingerprints, `replayed=true`, per-call item/link writes zero, unchanged row snapshots including all relevant audits and manifests. This is evaluation completion, **not** workflow completion; run stays queued. F0/F1 creation and gate audits precede the RB3 snapshot and are not confused with review writes. For every denial compare snapshots immediately before/after the denied invocation, including evaluation/items/links/audits; F1 itself may legitimately write gate and audit evidence.

## 4. Explicit conflict and smallest owner decision

**C-F0-C:** Frozen C describes pending input and verification blockers before correction, but F0's accepted `create_run_foundation` invokes the recovery inspector, whose selected-document preflight requires `extraction_status=verified`, verified active facts with matching doctor decisions and no open issues. The literal initial `needs_verification` C document cannot become an F0 manifest. F1 can HALT after selection when a previously clear selected source changes (existing `test_selected_unverified_fact_blocks_even_if_original_run_queued`); this is a controlled post-selection deterioration, not the historical initial OCR sequence. If a controlled C-shaped test stages three pending facts and the relevant flags **after** a clear F0 snapshot, retain `extraction_status=verified` and valid source identity solely to isolate F1's blocker branch; calculate expected issue *types* VI-001/002/003/005 from F1 and inspect exact `(type, reason, fact IDs)` rows, allowing multiple records per type. A `needs_verification` document instead makes F1 `unavailable=selected_document_preflight_unproven`, not HALT, because `document_not_verified` is outside its tolerated blocker set. Do not call either state real OCR. If exact controlled setup cannot achieve the expected HALT, stop and report observed behavior rather than altering F0/F1 or asserting success.

**Owner decision C only:** may RB4's bounded GOLD-C acceptance explicitly consist of (1) genuine F0 refusal of the initial blocked fixture, (2) a separately labelled genuine-run post-selection deterioration HALT test, and (3) a new genuine corrected-source PROCEED run, while recording that the original pending C never had a run-backed F1 HALT? Recommended **yes**, as a disclosed scope reconciliation, without changing frozen JSON or accepted services. If the owner requires literal initial-state run-backed HALT instead, stop: a separately designed and authorized F0/verification contract change is needed; no such production exception is included here. The owner's ratification marker in §7 must explicitly choose the recommended reconciliation, not silently override the frozen expectation. B's alternate offline values and D's selection/scaffold are resolved by the existing contracts and require no separate decision.

DR-006 is not silently disabled: unchanged RB2 may emit it if its conditions are met; accepted RB3 denies the **whole invocation** at T12 with `409 E_VALIDATION`, `dr006_persistence_not_authorized`, no writes, even alongside other flags. Whether a genuine F1-PROCEED source configuration reaches it remains unproven in both directions; F1 and RB2 have different conflict predicates and F2 restricts verified sources to selected documents. Reuse the accepted direct boundary regression; do not claim genuine reachability or persist DR-006/document spans. RB3-75..77 remain deferred/not executed.
