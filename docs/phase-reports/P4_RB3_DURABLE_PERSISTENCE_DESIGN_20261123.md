## 2. (A) Authority and authorization design

### 2.1 Proposed internal authenticated service boundary

```python
# backend/app/services/p4_rb3_review_persistence.py  (PROPOSED — does not exist)
def persist_run_review_items(
    db: Session, *, principal: Principal, run_id: str,
    validation_clock: datetime, upload_root: str,
) -> ReviewPersistenceReceiptV1: ...
```

Exactly five server-owned parameters. No parameter admits a clearance flag, gate decision, trusted-fact count, evidence-id list, policy override, lookback window, cached V2/RB1/RB2 object, idempotency token, request id or lineage claim: such inputs are structurally impossible, not merely ignored (**D-RB3-01**: internal authenticated service only; no HTTP router, agent tool, graph node, task or notification). The audit request identity is **derived internally** from immutable persisted identifiers (§8.4), never accepted from a caller.

`ReviewPersistenceReceiptV1` (new frozen dataclass, `backend/app/schemas/p4_rb3_review_persistence.py`, §8.3) reports a completed write; it is never an execution token and carries `runtime_evaluable=False`, `policy_status='unapproved'`, `demo_only=True`, `not_for_clinical_use=True`.

### 2.2 Authorization conditions (re-proved from stored rows inside the write transaction)

1. `isinstance(principal, Principal)` and `require_doctor(principal)` → else `403 E_FORBIDDEN`.
2. `run = db.get(WorkflowRun, run_id)`; missing → `404 E_NOT_FOUND`.
3. `run.doctor_id == principal.user_id` → else `403 E_FORBIDDEN`.
4. **Stored session including ownership:** a `UserSession` with `id == principal.session_id` **and `user_id == principal.user_id`**, `revoked_at IS NULL`, `parse_utc(created_at) <= validation_clock < parse_utc(expires_at)`; any parse error means **inactive** → else `403 E_FORBIDDEN`.
5. `User.role == Role.DOCTOR.value` and `User.is_active == 1` → else `403 E_FORBIDDEN`.
6. `Patient` exists, `data_source == 'synthetic_fixture'`, `patient.id == run.patient_id` → else `403 E_FORBIDDEN`.
7. `require_assigned_patient(principal, assigned_doctor_id=patient.assigned_doctor_id)` → `403 E_SCOPE_VIOLATION` on reassignment.
8. `run.status == 'queued'` → else `409 E_VALIDATION`.
9. Run version identity against `MAPPING_VERSION`, `WORKFLOW_VERSION`, `STATE_SCHEMA_VERSION`, `POLICY_REFERENCE_VERSION`, and `current_node`/`halt_reason`/`checkpoint_ref` all NULL → else `409 E_VALIDATION`.
10. Immutable demo clock: `run.as_of_utc == '2026-11-14T12:00:00Z'` and `parse_utc(run.as_of_utc) == to_utc(validation_clock)` → else `409 E_VALIDATION`.

**Clock semantics.** `validation_clock` is a fixed injected instant that **defines** the evaluation instant; `utc_now()` is never called. RB3 claims no wall-clock expiry detection: the only revalidation is re-testing that same instant against stored rows at T2 and T17.

## 3. (B) Fresh transactional verification — exact SQLite transaction ownership and lock boundary

### 3.1 Honest non-atomicity acknowledgements (normative)

1. **SQLite cannot transact with filesystem bytes**; `BEGIN IMMEDIATE` locks the database only.
2. **Re-hashing narrows but does not close the race.** RB3 re-hashes selected bytes at T3 (through the locked F1 re-check) and again at T17, as F2 does (`:330-344`). A change landing between the T17 re-hash and durable commit cannot be excluded by any SQLite transaction.
3. **Phase 1 performs no writes at all.** F2's `build_run_evaluable_review_evidence` takes its own `BEGIN IMMEDIATE`, projects read-only and **always rolls back** (`:470-473`); RB1's preview owns separate locks and also rolls back. Neither is a snapshot shared with Phase 2, and the three passes are never described as one transaction.
4. **RB3 owns exactly one committing transaction**, from T1's `BEGIN IMMEDIATE` to T18's single `db.commit()` or unconditional `db.rollback()`.
5. **No partial persistence:** items, links, the audit row and the completion record are written in that one transaction or not at all, and once the completion record exists the result set is **structurally sealed** against every insert and replacement path (G15–G17), and **every existing row of every RB3 table is protected against replacement in any run, before or after completion** (G18–G25).

### 3.3 Concurrency, replay and denial handling

`BEGIN IMMEDIATE` serializes writers; a second invocation resolves through T15 as exact replay or typed conflict, with `ux_review_evaluation_run`, **G17** and **G24/G25** as structural backstops (`IntegrityError` → rollback → conflict, never a partial write). Denials raise inside the transaction and roll back. A rolled-back attempt persisted nothing — no rows, no completion record, no audit row, and its UUIDs never existed — so a retry is a first evaluation; retry equivalence is **semantic** (§8.1).

## 4. (C) RB2-to-RB3 evaluator boundary

### 4.1 Pinned R3-A fixture clock vs the immutable persisted run clock

RB3 requires equality rather than reconciling by relaxation: a run is persistable only if `run.as_of_utc == '2026-11-14T12:00:00Z'` and `to_utc(validation_clock) == parse_utc(run.as_of_utc)`. Other clocks are denied, never converted; no wall clock is substituted (**D-RB3-04**).

### 4.2 Offline policy reference vs execution authority

The pinned R3-A policy is a bounded demo comparison reference. RB1 and RB2 both hard-code `policy_status='unapproved'` and `runtime_evaluable=False`. Persisting rows approves nothing and activates nothing; every item is bound to exactly one sealed policy revision through `review_item.policy_version` and `review_evaluation.policy_reference_sha256`.

### 4.3 Fixture-asserted lineage vs persisted provenance — decisive constraint and recommendation

Three verified facts decide this boundary: (1) RB2 admits only `{unavailable, fixture_asserted}` and rejects `stored_independently_verified` (`:221-225`; test `:275`), while its schema documents that value as "a FUTURE RB3 server-side state" (schema `:67-69`); (2) `TOOL_CONTRACTS.md:270` says `fixture_asserted` labels ***fictional*** lineage and that "a future RB3 verifier must instead query and prove the actual selected stored sources"; (3) labelling stored-proved rows `unavailable` is **not** neutral — RB2 then emits a `verified_lineage_unavailable` exclusion for every `verified_document`/`doctor_verified` row (`:317-322`), persisting **false exclusion claims**.

- **Alt A2 (recommended):** unchanged RB2 as pure computation core; `lineage_status='fixture_asserted'` passed **only** for rows whose stored lineage RB3 proved in-transaction, documented explicitly as a **transport label** forced by RB2's closed vocabulary. Every persisted artifact tells the truth: per-item `provenance_status` stores the evaluator's literal verbatim, per-item `stored_lineage_proved` records **RB3's own** independent in-transaction stored-lineage proof separately from that label (§6.1), `evidence_link` rows point at real stored rows of the same patient, and `review_evaluation.lineage_label_policy` records the ratified boundary option. Conditions: RB2 source/schema/tests frozen (zero diffs); no DR-006 item is ever persisted in this slice (§7.4); no trust promotion; mandatory RB3↔RB2 equivalence tests; append-only `TOOL_CONTRACTS.md` note (N8).
- **Alt B (fallback):** RB3-owned re-derivation of the six rules with `stored_independently_verified` as an RB3-internal state never passed to RB2. Honest labels, but ~500 lines of recently remediated bounded logic duplicated, divergence risk even with equivalence tests, a much larger review surface — and DR-006 becomes **inert by construction**, which would have to be disclosed. Alt B cannot be implemented by re-labelling, because RB2 rejects that value.
- **Alt C (rejected):** modify RB2 to accept `stored_independently_verified`; it reopens the owner-accepted candidate `8dd79ac0…` and edits frozen reviewed source and tests for no safety gain.

**Structural consequence of recommending A2 alone (RB3-R4-06E):** the writable vocabularies are pinned to that one option — `review_item.provenance_status = 'fixture_asserted'` and `review_evaluation.lineage_label_policy = 'a2_transport_label'` as **single-value** CHECKs. A stronger provenance assertion is **not** writable merely because Alt B appears in this document as an alternative; ratifying Alt B would require a re-proposed migration with the corresponding single-value CHECK. The transport-label tension remains **C-RB3-01, explicitly unratified** (§13).

### 4.7 RB3's end-to-end supported input domain (new; separates three things Revision 3 conflated)

**(a) RB2 pure-function guarantees** — R01–R08 hold **inside** `evaluate_p4_rb2_offline_fixture` for any typed input it accepts. They say nothing about code that runs before it.

**(b) Upstream adapter limitations (verified, not modified).** `compare_explicit_current_with_history` subtracts `timedelta(days=baseline_lookback_days)` from the **current** row's measurement stamp (`:132`) and subtracts `Decimal`s in the **ambient** context (`:148`). It has no `OverflowError` handler, and both accepted callers catch only `MonitoringInputError` (F2 `:308-309`; RB1 `:203-204`), so an `OverflowError` escapes F2's public wrapper too (which catches only `ValueError/TypeError/AttributeError`/`OperationalError`, `:430-474`). Probe results: `datetime.min(UTC) - timedelta(days=90)` and `- timedelta(days=365)` both raise `OverflowError: date value out of range`; the earliest stamp from which a 365-day subtraction is safe is `0002-01-01T00:00:00+00:00`. Because the subtraction is short-circuited behind `measure_type` **and** `unit` equality, it is reachable only when the out-of-domain current row has at least one usable historical row of the same measure type and unit. Probe results for Decimal: `decimal.DefaultContext` is `prec=28`, `ROUND_HALF_EVEN`, `Emin/Emax ±999999`, enabled traps `{InvalidOperation, DivisionByZero, Overflow}`; with an ambient `prec=5` the delta `121.123456789 - 100` silently becomes `21.123` instead of `21.123456789`; RB2's `_ARITHMETIC_CONTEXT` additionally traps `Inexact/Underflow/Clamped`, and applying it to an inexact operation **raised `Inexact`** — so it must not be imposed upstream; `localcontext` restored the caller's context on both normal exit and exception.

**(c) RB3's supported domain and conservative handling.** RB3 supports, end-to-end, exactly those runs in which **every** observation it will pass to the frozen comparator has a parseable `measured_at` satisfying `parse_utc(measured_at) >= 0002-01-01T00:00:00Z` — the bound that makes both the 365-day and 90-day lookback subtractions safe. Enforcement, with zero writes in every branch:

1. **T7 preflight** asserts the bound for every selected-current and L1-eligible historical row before any comparator call, denying `409 E_VALIDATION` reason `measurement_timestamp_out_of_supported_range`.
2. **P2/P3** catch `OverflowError` (and only that) from the frozen helper inside the read-only Phase-1 calls and map it to the same typed denial, so an out-of-domain run never surfaces as an uncaught crash or a `500`.
3. **RB3-owned pinned Decimal context:** the complete read/projection/write computation (T5–T16) runs inside `with localcontext(_RB3_ARITHMETIC_CONTEXT)`, where `_RB3_ARITHMETIC_CONTEXT = Context(prec=28, rounding=ROUND_HALF_EVEN, Emin=-999999, Emax=999999, capitals=1, clamp=0, flags=[], traps=[InvalidOperation, DivisionByZero, Overflow])` — **exactly the CPython default**, so it cannot change any accepted helper's behaviour while making an ambient leak impossible. It is entered once per invocation; `localcontext` restores the caller's context on success **and** on failure, including when a denial is raised. RB3 never sets `Inexact`/`Underflow`/`Clamped` traps, never mutates the thread-global context, and never modifies an accepted helper.
4. **Narrowly scoped future owner exception (identified, not taken):** widening the upstream comparator's window arithmetic to an overflow-safe difference comparison (as RB2 already does) would remove the domain restriction. That edits accepted P4-1 source and tests, so it is **out of scope** for this slice and would need its own owner marker; the conservative typed denial is preferred here.

No RB2 regression test is weakened, and no accepted F1/F2/RB1/RB2 source or test is changed by this design.

### 4.8 Active-fact derivation for `active_fact_verification_statuses` (RB3-R4-06C)

T9 derives the tuple **exactly** as F1 does (`p5_run_gate.py:342-348`): for each selected document, read its facts ordered by id, compute `verified_corrections = {f.corrected_from_fact_id for f in facts if f.corrected_from_fact_id and f.verification_status == 'verified'}`, and take `active = [f for f in facts if f.id not in verified_corrections]`; the tuple is `tuple(f.verification_status for f in active)` over all selected documents in canonical order. Consequences, all normative:

- A `pending` or `rejected` original that **no verified correction supersedes remains an active fact** and stays in the tuple. RB3 never drops it, never treats it as superseded, and never uses exclusion to make RB2's R05 pass.
- A rejected original that **is** superseded by a verified correction is not active, exactly as F1 computes it; RB3 does not re-decide correction lineage.
- Because F1 raises VI-005 `active_fact_unverified` for any active fact that is not `verified` (`:432`, `:523`), a run that reached a stored **PROCEED** gate necessarily has an all-`verified` active set; RB3 still derives and passes the tuple from stored rows and never assumes that outcome.
- Because every L1-eligible `verified_document` row must reference a fact on a **selected** document (F2 `source_reason`, `:187-193`), F1's active derivation over selected documents covers every fact relevant to R05; no unsupported `pending`/`rejected` source assertion can become an eligible RB2 input.

### 5.3 The three explicitly separate exclusion layers (RB3-R4-02, R4-S2)

**L0 — loader lineage diagnostics (not merged, not compared).** `provenance.lineage_exclusions` (`p4_readonly_provenance.py:186-190`, `:215`). Verified fact: **neither F2 nor RB1 reads this member.** RB3 therefore uses it only as a consistency diagnostic: every L0 `observation_id` must carry an **equal-or-stricter** L1 reason for the same observation (in practice `verified_lineage_unavailable`, because the loader's failure nulls `source_fact_id`/`source_document_id`/`source_fact_verification_status`, which L1's step 1a rejects). Any L0 id without such an L1 reason → `409 E_VALIDATION` "Stored lineage evidence is inconsistent." L0 is **never** unioned into L1 (Revision 3's instruction to do so is withdrawn) and **never** compared against F2's cached `history_exclusions`.

**L1 — exact F2-compatible eligibility/exclusion reconstruction.** For each record, in F2's order:

*Source-class step (the `source_reason` reproduction, applied **first**):*
1. `source == 'verified_document'`: require `source_fact_verification_status == 'verified'`, non-empty `source_fact_id`, **`source_document_id ∈` the re-pinned selected document set**, and `trust_level == 'doctor_verified'`; else L1 reason `verified_lineage_unavailable`. Then load the stored `ExtractedFact` by `source_fact_id` and require it exists with `patient_id == run.patient_id`, `document_id == source_document_id`, `field_name == 'value'`, `verification_status == 'verified'`; else `verified_lineage_unavailable`. Then select verified `test_name` facts on that document with `.limit(2)` and require **exactly one** with a non-empty `normalized_value`; else `verified_mapping_unproven`. Then normalize the alias (`" ".join(value.lower().strip().rstrip(":").split())`), look it up in `MAPPING_TABLE`, and require the mapped measure type to equal `observation.measure_type` and the mapped unit to equal **both** `observation.unit` and the stored value fact's `unit`; else `verified_mapping_unproven`.
2. `source ∈ {'patient_checkin', 'seed_fixture'}`: require `trust_level == 'self_reported_validated'` and `source_fact_id is None`; else `stored_trust_source_mismatch`.
3. Any other `source` value: `stored_trust_source_mismatch`.

*Admissibility step (applied **only when the source-class step returned no reason**):* call public `admissibility_reason(entry.observation, patient_id=run.patient_id, as_of_utc=parse_utc(run.as_of_utc))`; a `MonitoringInputError` from it becomes L1 reason **`malformed_history`** (exactly as F2 maps it at `:288-291`); a returned reason becomes the L1 reason verbatim (`validation_rejected`, `unit_mismatch`, `missing_timestamp`, `future_timestamp`).

*Emission rule:* **at most one L1 reason per non-selected observation**, appended as `(observation_id, reason)` in ascending observation-id order — never a union of all possible reasons. A row with an L1 reason is **not** fed to RB2.

*Selected-current rows are never L1-excluded:* mirroring F2 (`:239-276`), a selected row that fails the source-class step, whose manifest fields changed, whose `admissibility_reason` raises, which is inadmissible, or whose `measured_at` will not parse causes a **typed denial of the whole invocation** (`409 E_VALIDATION`), not an exclusion.

**L2 — the evaluator's own exclusions.** `result.excluded` captured **verbatim** from the frozen evaluator at T11, in its own order (sorted by `(observation_id, reason)`, `:490-499`). L2 reasons are `validation_rejected`, `unit_mismatch`, `missing_timestamp`, `future_timestamp` (RB2's **no-skew** variant), `missing_created_at` and `verified_lineage_unavailable` (R02). An eligible row may carry **two** L2 exclusions (`:315-322`). **L2 is never compared against F2's `history_exclusions`** — only L1 is.

**The 5-minute skew divergence, resolved conservatively.** `admissibility_reason` admits `measured_at` up to `MAX_FUTURE_SKEW_MINUTES = 5` after the clock (`monitoring.py:125-126`, `core/clock.py:23`), while RB2 excludes a row **strictly after** its pinned clock (`:302-305`). For a row measured in `(clock, clock + 5min]`: L1 admits it (so it is fed to the evaluator exactly as F2 and RB1 would), and L2 reports `future_timestamp`. RB3 therefore (a) does **not** pre-filter such rows — pre-filtering would change the evaluator's input relative to F2 and loosen `monitoring`'s accepted contract; (b) does **not** treat the L2 exclusion as an L1 disagreement; (c) surfaces both layers truthfully in the receipt; and (d) neither contract is weakened, skipped or replaced.

**Cross-check, never authority.** The L1 non-selected exclusion set (ids **and** reason codes, in ascending order) must equal `evidence.history_exclusions` and `preview.history_exclusions`; any difference → `409 E_VALIDATION` "Historical exclusion evidence changed." An L1 exclusion that is also a selected current id → `409 E_VALIDATION` "Selected current evidence may not be excluded." Because L1 reproduces F2's complete contract **and** precedence, this equality is expected to hold on valid paths rather than spuriously failing. A residual divergence found during implementation is a **stop-and-escalate** condition for a new owner decision — not a licence to weaken the cross-check or to prefer the cached set.

**L3 — merged receipt view.** `receipt.excluded_evidence` is the canonical merge of L1 and L2, deduplicated on `(observation_id, reason_code)` and ordered ascending by that pair; `review_evaluation.exclusion_count` is `len(L3)` (§6.3 for the derived bound). No truncation is ever applied to satisfy a bound.

### 5.5 Detection of added, removed or modified eligible history

| Change | Detected by | Mechanism |
|---|---|---|
| New eligible historical row | F1 digest **and** RB3 identity | F1 lists every patient observation; T3 compares to the persisted PROCEED row. Independently the row appears in `history_observations` |
| Eligible row deleted | F1 digest **and** RB3 identity | Both; also breaks the L1 cross-check if it had been excluded |
| Non-baseline row's value/unit/trust/validation/source/`measured_at` changed | F1 digest **and** RB3 identity | **The exact case the F2 projection member misses**; F2's digest still changes **indirectly** through its embedded F1 member (`:352`) |
| Non-baseline row's `created_at` changed | F1 digest **and** RB3 identity | F1 serializes `obs.created_at`; F2 does not serialize it directly; DR-008's ordering evidence is protected |
| `Document.uploaded_at`, `failure_code` or patient-ref changed | F1 digest **and** RB3 identity | Both serialize the same fourteen document fields |
| `FactVerification.decision`/`decided_at`/`source_image_compared` changed | F1 digest **and** RB3 identity | Both serialize the real decision columns |
| Eligibility changed with no column change | RB3 identity + L1 cross-check | `l1_exclusions` changes; equality with the cached sets fails |
| A row's source document leaves the selected set | T6 L1 step 1a | Excluded `verified_lineage_unavailable`; T4 manifest equality also fails |
| Active-fact set changed (a verified correction added) | RB3 identity + F1 digest | `active_fact_verification_statuses` and `verified_facts` change; R05 re-evaluated |
| Baseline comparison unchanged but rule output changed | T15 output comparison | Complete input **and** output identities are compared together (§8.2) |
| Source bytes changed on disk | T3 and T17 re-hash | Race reduced, not eliminated (§3.1) |
| More than 100 patient observations | F1 and the loader | `too_many_patient_observations` / `400` "Too many scoped observations." |

### 5.6 Sole authoritative history source — no separate pre-write pin

The fresh locked snapshot (T5–T6) is **explicitly the sole authoritative history source**. No pre-write history pin table is created: a second persisted history copy would need its own immutability guards, downgrade refusal and reconciliation story for no detection gain, since the F1 digest covers stored-row integrity and the RB3 input identity covers derived rule-input identity. Phase 1's preview remains a corroborating drift cross-check only.

### 5.7 Pre-commit revalidation and filesystem limitation

T17 repeats the locked F1 re-check, the stored-PROCEED fingerprint equality, the byte re-hash and the input-identity recomputation immediately before T18's single COMMIT; any difference rolls back with a typed denial. The proposed RB3 module docstring restates §3.1 so no future reader mistakes re-hashing for atomicity.

### 5.8 Does exact correctness require changing accepted F1/F2/RB1 paths?

**No.** All interfaces are public (§1.3); the history, empty-selection, eligibility-precedence and arithmetic-domain gaps are closed inside RB3 (§5.2, T8a, §5.3, §4.7). The only proposed touch is the docstring-only E6 clarification. Explicitly **not** proposed (each would need its own owner exception): exporting `COMPARISON_HISTORY_VERSION`/`HISTORY_LOOKBACK_DAYS` from `p5_evidence_bridge`; exporting `POLICY_CANONICAL_SHA256`/`POLICY_LOOKBACK_DAYS` from `p4_run_bound_preview`; making `source_reason` public (RB3 reproduces its contract and precedence instead, and the L1 cross-check is the equivalence proof); widening `compare_explicit_current_with_history`'s window arithmetic (§4.7(c)(4)); setting `PRAGMA recursive_triggers=ON` in `db/session.py` (§6.4a).

G15–G17 keep their Revision-4 SQL verbatim. **Identity → guard mapping (complete):** `review_item`: PK → G18, `ux_review_dedupe` → G19, `ux_review_order` → G20, post-completion run seal → G15; `evidence_link`: PK → G21, `ux_evidence_link_observation` (effective) → G22, `ux_evidence_link_span` (prospective) → G23, NULL-safe typed 8-column identity → G11 (defence in depth), post-completion owner-run seal → G16; `review_evaluation`: PK → G24, `ux_review_evaluation_run` → G25 + G17, full scope/audit/count consistency → G14. **Every unique identity of every RB3 table now has a `BEFORE INSERT` guard, and none of them depends on the target run having completed.**

**Why the Revision-5 guards are necessary (probe-measured, `recursive_triggers = 0` as configured by `db/session.py:23-33`).** With G1–G17 alone, `INSERT OR REPLACE`/`REPLACE INTO` **silently succeeded** in six distinct situations: a same-run **primary-key** replacement **before** completion; a same-run `(workflow_run_id, dedupe_key)` replacement before completion; a same-run `(workflow_run_id, display_order)` replacement before completion; and a **cross-run** replacement of a completed `review_item`, `evidence_link` or `review_evaluation` row (the new row named a run that had not completed, so G15/G16/G17 — which inspect `NEW.workflow_run_id` or the new owner's run — did not fire). The cross-run `review_item` case was measurably destructive: the sealed run-A completion row still recorded `item_count = 1` while run A then held **0** items, so the durable record became **false** rather than merely incomplete. G15–G17 were nevertheless correct for what they covered — same-run post-completion inserts of any kind, and a same-run `ux_review_evaluation_run` replacement (G17 caught it) — and are retained unchanged. G18–G25 close the remainder by making the *existing row*, not the *target run*, the protected subject.

**Measured preservation requirements (all probe-verified with G18–G25 installed):** the valid initial T16 sequence (items → links → audit → completion) still inserts successfully; a second independent run still persists its own complete sequence while the first run is sealed, with the sealed run's rows byte-identical and its recorded counts unchanged; `PRAGMA recursive_triggers` stays **0**; `backend/app/db/session.py` is not edited; no accepted P2 behaviour changes.

**Rejected alternatives (Revision 5):** (i) `PRAGMA recursive_triggers=ON` — still rejected: connection-level pragma, edits accepted P2 source outside the allowlist, changes trigger recursion semantics database-wide. (ii) Relying on FKs — **rejected and measured to be insufficient**: `PRAGMA foreign_keys=1` blocked a replacement only when it **changed** the PK of a parent that still had a child `evidence_link` (`FOREIGN KEY constraint failed`), while a **PK-preserving** overwrite of that same parent **succeeded silently** because the child's reference is satisfied again at statement end; linkless items, `evidence_link` rows and `review_evaluation` rows have no child references at all. The design therefore **never relies on FKs for immutability** (§6.6). (iii) Widening G15/G16/G17 to inspect existing rows rather than adding guards — semantically conflates sealing with identity protection and loses per-identity diagnostics.

**Firing-order independence (measured).** When several guards match one statement, SQLite reports from the **most-recently-created** matching trigger: with creation orders `(pk, a, b)`, `(b, a, pk)`, `(a, pk, b)`, `(pk, b, a)` the reported messages were `MSG-B`, `MSG-PK`, `MSG-B`, `MSG-A`. Every guard aborts regardless of order, and the outcome is deterministic for a fixed creation order, but **which** message appears in a multi-conflict statement is an artifact of creation order. Tests must therefore assert **rejection and unchanged rows** for multi-conflict statements and may assert the documented message only for single-conflict statements (§11, RB3-108).

**`INSERT OR IGNORE` (measured).** A trigger's `RAISE(ABORT, …)` is **not** suppressed by an outer `INSERT OR IGNORE` conflict clause: the statement aborted and no row changed. `INSERT OR IGNORE` therefore cannot silently skip a required row without also tripping G14/G25's count and one-completion consistency and T17's pre-commit revalidation.

**Revision-4 finding, retained: why the three run seals exist (probe-verified, `recursive_triggers = 0` as configured by `db/session.py:23-33`).** With only G1–G14, a completed run's result set was **not** sealed: `INSERT OR REPLACE` and `REPLACE INTO` on a conflicting `review_item`/`evidence_link`/`review_evaluation` row **succeeded and silently replaced the row**, because SQLite's REPLACE resolution deletes the conflicting row and **`BEFORE DELETE` triggers do not fire for that internal deletion unless `recursive_triggers` is enabled** — so G2/G6/G13 did not cover it. Plain UPDATE, `UPDATE OR REPLACE` and upsert `DO UPDATE` were blocked by G1/G5/G12, and upsert `DO NOTHING` changed nothing. A `BEFORE INSERT` trigger, by contrast, fired for **every** insert path (plain, `OR REPLACE`, `REPLACE INTO`, upsert `DO UPDATE`, upsert `DO NOTHING`), and conditioning it on an existing completion row blocked all five late-insert paths on both a child table and the completion table itself, while the initial items → links → audit → completion sequence and other runs were unaffected. G15–G17 are that mechanism.

**Rejected alternative (Revision 4, superseded by the fuller Revision-5 list above):** setting `PRAGMA recursive_triggers=ON` would also make REPLACE honour the DELETE guards, but it is a **connection-level** pragma the repository does not set (`session.py:31` sets only `foreign_keys=ON`), changing it edits accepted P2 source outside this task's allowlist, and it alters trigger recursion semantics for **every** table in the database. Not proposed; recorded as **C-RB3-09**. Revision 5 additionally shows it would still be **insufficient on its own** for cross-run replacement, because a `BEFORE DELETE` guard fires only for the row being deleted and cannot distinguish a legitimate first insert from a replacement.

Requested INSERT restrictions → guards: `state='open'` → G3; real run ownership → NOT NULL FK + G4/G14; equal run/item patient and policy version → G4; same-patient evidence → G10; existing review-item owner → G9; unsupported `verification_issue`/`summary_claim` owners → G7; reserved `document_span`/`checkin_note` kinds → G8; duplicate typed evidence identity → UNIQUE indexes + G11; **post-completion insertion or replacement → G15/G16/G17**; **replacement of any existing unique identity, in any run, before or after completion → G18–G25**; **audit/completion cross-consistency → G14 (§6.4a)**.

#### 6.4a G14's complete scope, and the structural vs application-layer split

G14 (a single `BEFORE INSERT` trigger on `review_evaluation`) aborts unless **all** of the following hold, each expressible as a subquery-free comparison or a `SELECT` on another table:

1. **Run match:** a `workflow_run` row with `id = NEW.workflow_run_id` exists, and `NEW.patient_id`, `NEW.doctor_id`, `NEW.policy_version`, `NEW.as_of_utc` equal that run's `patient_id`, `doctor_id`, `policy_version`, `as_of_utc`.
2. **Gate match:** a `run_gate_evaluation` row with `id = NEW.gate_evaluation_id` exists, belongs to the same `workflow_run_id`, has `decision = 'proceed'`, and its `gate_version` and `input_fingerprint_sha256` equal `NEW.gate_version` and `NEW.gate_input_fingerprint_sha256`.
3. **Audit match (eight structural comparisons, RB3-R5-03):** an `audit_event` row with `id = NEW.audit_event_id` exists and its `workflow_run_id`, `subject_type`, `subject_id`, `actor_type`, `actor_id`, `outcome`, **`event_type`** and **`patient_id`** equal `NEW.workflow_run_id`, `'workflow_run'`, `NEW.workflow_run_id`, `'user'`, `NEW.doctor_id`, `'ok'`, **`'workflow.review.persisted'`** and **`NEW.patient_id`** — i.e. the audit event's kind, subject, run, actor **and patient** all match this evaluation (§8.4). Revision 4 checked only the first six, so a completion row referencing an audit row of a *different event type* or a *different patient* was structurally accepted even though §8.2 (5) expects both to match; both comparisons were probe-verified to reject independently, and a fully consistent row is still accepted (no over-blocking).
4. **Row-count match:** `NEW.item_count = (SELECT COUNT(*) FROM review_item WHERE workflow_run_id = NEW.workflow_run_id)` and `NEW.evidence_link_count = (SELECT COUNT(*) FROM evidence_link WHERE owner_type = 'review_item' AND owner_id IN (SELECT id FROM review_item WHERE workflow_run_id = NEW.workflow_run_id))`.
5. **No orphan or duplicate completion:** `ux_review_evaluation_run` plus **G17** and **G25** make a second or *replaced* completion row for the run impossible by any insert or replacement path, **G24** makes a primary-key overwrite of an existing completion row impossible in any run, and G15/G16 plus G18–G23 make post-completion child rows and any overwrite of an existing child row impossible — so a completion row can never be orphaned from, or inconsistent with, its result set.

**Structural (enforced by the database, surviving any client that bypasses the service layer):** all five G14 conditions, **including the eight audit comparisons of condition 3 (`event_type`, `patient_id`, `workflow_run_id`, `subject_type`, `subject_id`, `actor_type`, `actor_id`, `outcome`)**; G1–G13 immutability and vocabulary; G15–G17 run sealing; **G18–G25 replacement protection for every unique identity of every RB3 table, independently of run completion**; every `length()`/range/literal CHECK; all FKs with `ON DELETE RESTRICT` and `PRAGMA foreign_keys=ON`; `ux_review_dedupe`, `ux_review_order`, `ux_review_evaluation_run` and both partial unique indexes.

**Application-layer only (asserted in service code and tests, **not** structurally enforceable in SQLite):** equality of `input_fingerprint_sha256`/`output_identity_sha256` with values recomputed at T10/T14/T17; the L1↔cached exclusion cross-check; span resolvability against `document_page_text` (a CHECK cannot call a Python helper or compare substrings across tables); the exact insertion **order** within T16 (immediate FKs constrain only the audit-before-completion and item-before-link pairs); the derived `stored_lineage_proved` boolean; the DR-006 prohibition (T12 denies before any row exists, so no DR-006 row can appear — but the database itself would accept one if some other writer inserted it, which is why `dr006_policy` and G8's kind restriction are the structural parts); the audit `safe_detail` **content** — its *key set, ordering and value equality* are verified by the service and tests, while its **length bound is now guaranteed by construction** rather than by truncation (§8.4, RB3-R5-02) and the column bound itself is `String(500)`; and the sealed-policy digest's correspondence to the actual policy file bytes. Each is listed here so no reader infers structural enforcement that does not exist.

### 6.5 Index and uniqueness inventory, including SQLite NULL semantics

SQLite treats NULLs as **distinct** in UNIQUE indexes — a behaviour this repository already relies on deliberately (`ux_obs_source_fact` on the nullable `observation.source_fact_id`, `0003:263`).

1. **Partial UNIQUE indexes** on the accepted `sqlite_where` pattern (`0002:289`; ORM mirror `models.py:278-287`; reflected by name in `check_alembic_smoke.py:513-520`):
   - `ux_evidence_link_observation UNIQUE (owner_id, observation_id) WHERE kind = 'observation'` — all indexed columns NOT NULL for that kind → **fully effective, and the only effective evidence-identity index in this slice**, since G8 makes `observation` the sole writable kind.
   - `ux_evidence_link_span UNIQUE (owner_id, document_id, page_index, char_start, char_end) WHERE kind = 'document_span'` — declared for ORM/migration parity and for the future DR-006 extension, but **inert in this slice** because G8 makes `document_span` unwritable. Stated explicitly rather than presented as active protection; it becomes effective only under a future owner decision that also relaxes G8, and §6.2's kind-conditional CHECK already guarantees its columns are NOT NULL when that happens.
2. **G11** is retained as defence-in-depth, not as the primary mechanism. It matches the **typed eight-column identity** NULL-safely with `IS`, which is *strictly stronger* than any unique index (it also covers `checkin_note` and cross-kind tuples the indexes do not), and it fires `BEFORE INSERT` so it cannot be bypassed by a replacement path.
3. **Every declared UNIQUE identity has a matching `BEFORE INSERT` replacement guard (RB3-R5-01):** `ux_review_dedupe` → G19, `ux_review_order` → G20, `ux_review_evaluation_run` → G25, `ux_evidence_link_observation` → G22, `ux_evidence_link_span` → G23, plus the three primary keys → G18/G21/G24. This pairing exists because a UNIQUE index alone is **not** immutability protection under SQLite's REPLACE conflict resolution: the index is satisfied by *deleting* the existing row and inserting the new one, and with `recursive_triggers = 0` no `BEFORE DELETE` guard fires for that internal deletion (§6.6). The inert `ux_evidence_link_span` still gets its guard (G23) so the protection is complete **prospectively**: if a future owner decision relaxes G8, span rows are already replacement-protected without a further trigger migration. Both partial-index guards mirror their index's `WHERE` predicate exactly and use `=` rather than `IS`, so they neither over-block nor tighten SQLite's NULL-distinct UNIQUE semantics (probe-verified: a `document_span` row for the same owner is not blocked by G22, a different span for the same owner/document/page is allowed, each duplicate identity is rejected by its own guard, and the same observation under a different owner is allowed).

Rejected (**C-RB3-04**): a single COALESCE **expression** UNIQUE index — it would need `Index(..., text(...))` in the ORM, and `test_migration_matches_the_orm_metadata` (`tests/p2/test_p2_migration.py:314-331`) compares reflected index **names** to ORM-declared names for every table; the repository has no expression-index precedent, so its reflection parity is unproven. If the owner prefers it, the implementation PR must first prove name-level parity with a dedicated test.

Also unique: `ux_review_dedupe`, `ux_review_order`, `ux_review_evaluation_run`.

### 6.6 SQLite constraint behaviour accuracy (normative for the implementation PR)

`TEXT(n)` length is **not** enforced → every bound is an explicit `length()` CHECK (`0006:136` precedent); tests must assert the CHECK, never the type declaration. CHECK cannot reference other tables → cross-table integrity is triggers (G4, G9, G10, G14, G15, G16, G17). No regex in CHECK → closed IN lists plus length checks. FKs need `PRAGMA foreign_keys = ON`, set per connection at `db/session.py:31` and asserted by `tests/test_database.py:160`; **FKs are immediate and no deferred constraint is used anywhere in this design**. **`recursive_triggers` is OFF** (never set) → `BEFORE DELETE` guards do **not** cover the REPLACE conflict-resolution path, which is why G15–G17 are `BEFORE INSERT` guards (§6.4). Triggers are invisible to ORM metadata → assert them via `sqlite_master WHERE type='trigger'`, as `check_alembic_smoke.py:498-501` already does. Batch mode recreates tables → RB3 creates new tables only and alters none, so no accepted CHECK, index or row can be silently dropped.

**Revision-5 additions (all probe-measured, normative for the implementation PR):**

1. **A UNIQUE index is not immutability protection.** Under REPLACE resolution SQLite *satisfies* the index by deleting the conflicting row and inserting the new one; with `recursive_triggers = 0` the `BEFORE DELETE` guards (G2/G6/G13) never fire for that internal deletion. Protection therefore has to be a `BEFORE INSERT` guard that inspects the **existing** rows (G18–G25), not the statement's conflict clause.
2. **FKs give only partial, incidental protection and are never relied on.** Measured: replacing a parent `review_item` with a **different** primary key while a child `evidence_link` still referenced it failed with `FOREIGN KEY constraint failed`; replacing that same parent while **preserving** its primary key **succeeded silently**, because the child's reference is satisfied again by statement end. Linkless items, `evidence_link` rows and `review_evaluation` rows have no child references, so they had no FK protection at all. Immutability comes from G1/G5/G12 (UPDATE/DELETE), G15–G17 (run seals) and G18–G25 (identity replacement) — never from FK side effects.
3. **A trigger's `RAISE(ABORT, …)` is not suppressed by an outer `INSERT OR IGNORE`.** Measured: the statement aborted and no row changed. `INSERT OR IGNORE` cannot be used to skip a guard, and a silently skipped *required* row would in any case trip G14's count match, G25/G17's one-completion rule and T17's pre-commit revalidation.
4. **Multi-trigger firing order is creation-order dependent and must not be relied on.** Measured: with several matching `BEFORE INSERT` triggers on one table, the **most-recently-created** one reported; four different creation orders produced three different messages, each deterministic for its order. Tests must assert *rejection and unchanged rows* for multi-conflict statements, and may assert a documented message only for single-conflict statements (RB3-108).
5. **Partial-index guards must mirror the index predicate.** A guard on `(owner_id, observation_id)` without `kind = 'observation'` on both sides would over-block other kinds; G22/G23 mirror their predicates and use `=` (matching SQLite's NULL-distinct UNIQUE semantics) while G11 remains the strictly stronger NULL-safe defence-in-depth trigger.
6. **Cross-run replacement is the destructive case.** Measured damage: after a cross-run primary-key replacement of a completed run's item, that run's sealed completion row still recorded `item_count = 1` while the run held `0` items — the durable record became **false**, not merely stale. G15–G17 could not see it because they inspect the *new* row's run; G18–G25 see the *existing* row.

### 6.6a Trigger creation order in the proposed migration

All three tables and their indexes are created first, then all 25 triggers — no trigger reads a table created later in the same migration (`audit_event` and `workflow_run` have existed since `0002`/`0003`, `run_gate_evaluation` since `0007`). Within a table the guards are created in inventory order (G1…G25); because every guard independently aborts, the measured creation-order firing behaviour (item 4 above) changes only *which* message is reported for a multi-conflict statement, never whether the statement is rejected. Downgrade drops the triggers in reverse creation order before the indexes and tables (§9.1).

### 6.7 ORM / migration parity obligations

`test_migration_matches_the_orm_metadata` (`:314-331`) asserts migrated tables equal `Base.metadata.tables` and, per table, migrated index **names** equal declared index names. The implementation PR must therefore declare all three tables and every index (including both partial unique indexes with matching `sqlite_where` text, even the inert one) in `backend/app/db/models.py` **and** create identical names in `0008`. Triggers are migration-only and asserted separately. Any name mismatch fails an accepted test — a hard obligation, not a style preference.

### 6.8 Referential integrity and deletion restrictions

All RB3 FKs are `ON DELETE RESTRICT`, preserving the dictionary's deletion restrictions and the accepted `audit_event`/`verification_issue` → `workflow_run` pattern (`0006:143-152`). `review_item.workflow_run_id` stays NOT NULL with a genuine run parent; no placeholder, synthetic or shadow run row is ever created. Deletion of any referenced run, patient, user, document, observation, gate evaluation or audit row is structurally refused. The only removal path remains the demo reset (whole-database rebuild).

## 7. (E) Evidence-link mapping

### 7.1 RB2 evidence keys → typed persisted links (this slice)

RB2 emits `observation:<id>`, `document:<id>` and `fact:<id>` keys (`_flag:160`). **Verified: `extra_evidence` is passed by exactly one call site — DR-006 (`:443-454`); DR-001/003/005/008/009 pass only `rows`.** Since D-RB3-08(ii) prohibits persisting any DR-006 result, the only keys that can occur in an authorized invocation are `observation:<id>`:

| RB2 key | Persisted link | Proof required at T13 |
|---|---|---|
| `observation:<id>` | `kind='observation'`, `observation_id=<id>`, `document_id` and all span columns NULL | Stored `Observation` exists, same patient (also G10), and is in the re-pinned selection or the L1-eligible set |
| `document:<id>` | **not writable in this slice** (G8) | Reserved for the future DR-006 extension (§7.2a); if such a key ever appears, T13 denies the invocation as unresolvable |
| `fact:<id>` | **not writable in this slice** (G8) | Same |
| `checkin_note` | **never written by RB3** (G8) | Reserved vocabulary for a future check-in slice; no rule emits one |

**Deny, never fabricate.** An unresolvable key denies the **entire** invocation (`409 E_VALIDATION`); RB3 never fabricates an id, never substitutes a NULL or free-text reference, and never invents a fact or verification decision. Fixture-declared references are not automatically authorized evidence: every key must resolve to a stored row of the same patient under the lock.

### 7.2 Per-rule mapping (authorized slice)

| Rule | Reason code (actual) | RB2 evidence (actual call site) | Refs | Persisted links |
|---|---|---|---|---|
| `DR-001` missing **baseline** | `missing_baseline` | `(current,)` (`:344-353`) | 1 | 1 `observation` |
| `DR-003` stale measurement | `measurement_stale` | `(newest,)` (`:361-370`) — may be a historical row per the owner clarification | 1 | 1 `observation` |
| `DR-005` change exceeds demo parameter | `change_exceeds_demo_parameter` | `(baseline, current)` (`:390-401`) | 2 | 2 `observation` |
| `DR-008` duplicate / out-of-order | `duplicate_or_out_of_order` | `(first, second)` (`:452-479`) | 2 | 2 `observation` |
| `DR-009` implausible value | `implausible_value` | `(current,)` (`:408-417`) | 1 | 1 `observation` |
| `DR-006` verified source conflict | `verified_source_conflict` | `(first, second)` **plus** four document/fact refs (`:423-454`) | 6 | **none — the whole invocation is denied at T12** (§7.4); mapping preserved as §7.2a |

Authorized maxima: **2** references per persistable flag, **12** items (4 measure types × `max_items_per_type` 3), therefore **24** links — the bound encoded in §6.3.

### 7.2a Future DR-006 extension design (specified, **not** an authorized writable path)

Preserved in full so a future owner decision can ratify it without redesign, and explicitly **not** writable in this slice:

- **Six keys:** `observation:first`, `observation:second`, `document:first`, `document:second`, `fact:first`, `fact:second` (`_flag:160` + `:434-439`) → **six** links: two `observation` (neither row may be dropped), two `document_span` from each document's stored verified `test_name` fact, two `document_span` from each stored verified `value` fact. All six are pairwise distinct (two distinct observation ids; four spans across two distinct documents with different coordinate ranges), so G11 and both partial unique indexes hold without collision.
- **Span contract:** `document:<id>` → the stored verified `test_name` fact's exact span; `fact:<id>` → the stored verified `value` fact's exact span. Every span must satisfy `EXTRACTION_PROVENANCE.md` §5 rule 1 — `0 <= char_start < char_end <= len(page_text)`, within the persisted 20,000-character bound that `DocumentPageText`'s CHECKs enforce structurally, and `page_text[char_start:char_end] == raw_text[:300]` against the persisted `document_page_text` row — asserted with the public `span_is_resolvable` (`documents/field_parser.py:555-566`) or, if its typed input cannot be constructed without inventing fields, by asserting the identical condition directly (the same contract, never a weaker one). A missing or unresolvable span denies the **whole** invocation; coordinates are never fabricated and a NULL span is never a substitute for provenance.
- **Structural maximum:** 12 items × 6 references = **72** links.
- **What ratifying it would require:** its own owner decision; a migration relaxing G8 to permit `document_span`, raising `evidence_link_count` to `0..72`, making `ux_evidence_link_span` effective and adding `dr006_policy='persisted'` as a writable value; genuine provenance evidence for the persisted items; an append-only `DEMO_REVIEW_RULES.md` note; and new acceptance cases. **None of that is authorized here, and nothing in this slice silently widens any bound.**

### 7.3 Kind semantics

`observation` = this stored observation row, same patient, enforced by G10 — the only writable kind in this slice. `document_span` = a persisted document at a stored, resolvable span; reserved (§7.2a). `checkin_note` = reserved vocabulary for a future patient-check-in slice (§5 of the contract requires the note-bearing `observation_id`), never written by RB3 because none of the six rules emits a check-in reference. No free-text evidence link exists and none is invented; no verification decision is fabricated — `verified_by_user_id`, `decided_at` and `FactVerification` rows are read as stored and captured in the input identity rather than re-decided.

### 7.4 DR-006: conservative persistence prohibition (**C-RB3-02**, **C-RB3-08**, **D-RB3-08(ii)**)

**Recommended and designed-for policy: option (ii), the conservative prohibition.** All six RB2 rules remain **unchanged**; the evaluator is invoked exactly as accepted and its DR-006 detection is neither weakened nor bypassed. If the result contains **any** DR-006 flag, T12 denies the **entire** persistence invocation with:

```
409 E_VALIDATION   reason: dr006_persistence_not_authorized
```

Never a silently dropped item, never a persisted subset, never a partial write. `review_evaluation.dr006_policy` is CHECK-pinned to `'prohibited_denied'`, and the receipt reports `dr006_policy='prohibited_denied'` or `'not_present'` only.

**This is a deliberate proposed scope reduction, recorded as such:** a run whose evidence genuinely produces a verified-source conflict yields **no persisted review items at all**, rather than a persisted subset. That reduction is visible in the receipt, in `N13`'s append-only `DEMO_REVIEW_RULES.md` note, and in this section; it is not presented as a neutral outcome.

**Reachability is UNPROVEN in both directions, and no fixture is invented.** Revision 1's "structurally unreachable" claim and Revision 2's non-selected-document fixture are both withdrawn: F2's `source_reason` excludes any `verified_document` row whose `source_document_id` is not in the selected document set (`:187-193`), so that fixture cannot reach the evaluator. The verified mechanism divergence remains: DR-006 iterates `combinations(ordered, 2)` over all eligible rows of a measure type on **exact** `measured_at` equality with distinct document **and** fact ids (`:423-441`), while F1's VI-006 loop covers **selected documents only** (`p5_run_gate.py:608`), `continue`s — constructing no candidate — unless the document has exactly one `test_name`, one `report_date` and one verified `value` fact with a mapped alias and matching unit (`:617-628`), and compares on UTC calendar day (`documents/issues.py:243-256`); F2's `source_reason` has **no** `report_date` requirement. Whether a genuine F1-PROCEED run can reach DR-006 also depends on extraction-time issue generation (VI-001…VI-005) and F1's selected-document preflight (`:515-528`), which this design has not fully traced. The only asserted facts are that divergence and that the currently approved fixtures do not exercise it (`GOLD-D.expected.json` records `expected_source_conflicts: 0`) — a fixture property, not an invariant.

**Consequences for testing and scope.** A **direct unit-level boundary test** may and should prove the whole-invocation denial by feeding the evaluator two qualifying stored-proved rows and asserting that RB3 denies with `dr006_persistence_not_authorized` and zero writes. **Such a test does not prove end-to-end reachability**, and it is never reported as doing so. **No invented F1-PROCEED fixture is required to close this conservative slice**: because the prohibition denies whatever the evaluator emits, the slice is complete without settling reachability. **C-RB3-08** therefore remains an *open documentation obligation for a future extension*, not a blocker for this slice: any future DR-006 persistence extension must first either construct a genuine PROCEED run reaching DR-006 through the accepted F1/F2 contracts, or prove from the accepted extraction/issue logic that none exists — and must supply genuine provenance evidence for the items it proposes to persist.

## 8. (F) Idempotency, replay and atomicity — invocation level

### 8.1 Identities

- **Dedupe key (unchanged, per row):** `sha256("|".join((patient_id, rule_id, *sorted_refs, trust_basis)))` from the frozen evaluator (`:164`), with `_valid_id` refusing `|`/control chars (`:176-188`); persisted with `UNIQUE (workflow_run_id, dedupe_key)`.
- **Complete input identity:** `review_evaluation.input_fingerprint_sha256`, computed at **T10** over the actual constructed input (§5.4).
- **Complete semantic output identity:** `review_evaluation.output_identity_sha256`, computed at **T14** = the same canonical JSON+SHA-256 discipline over the persisted **semantic** output: for each item in evaluator order, `(display_order, rule_id, reason_code, workflow_hint, trust_basis, message, policy_version, dedupe_key, state, provenance_status, stored_lineage_proved)` together with its ordered evidence-link tuples `(kind, document_id, observation_id, page_index, char_start, char_end)`; plus `item_count`, `evidence_link_count`, `lineage_label_policy`, `dr006_policy`, the **L2 exclusions verbatim** as `(observation_id, reason)` in evaluator order, and `span_proofs` — `[[document_id, fact_id, field_name, page_index, char_start, char_end, resolvable]]`, which is **structurally empty (`[]`) in every authorized invocation of this slice** because no `document_span` link can be written (§7.2a). An empty list is hashed as `[]`, never omitted, so the identity shape is stable and no uninitialized value is ever hashed.
  **`provenance_status` and `stored_lineage_proved` are both included**, so the identity cannot be preserved while either per-item provenance representation changes.
  **Deliberately excluded:** `review_item.id`, `evidence_link.id`, `review_evaluation.id`, `audit_event_id` and every `created_at` — per-invocation surrogate values whose inclusion would make an exact semantic replay compare unequal. Their exclusion cannot mask a content difference because every semantic field the evaluator emitted, plus RB3's own per-item lineage proof, is included. This is the precise sense in which retry equivalence is semantic and newly generated UUIDs need not match a rolled-back attempt.

### 8.2 Replay cases, exact validation and deterministic conflict precedence

**Exact replay validation (case 1) requires all of the following — a matching audit FK or a matching per-row dedupe key is explicitly insufficient:**

1. **Completion metadata:** the stored `review_evaluation` row's `fingerprint_version`, `input_fingerprint_sha256`, `output_identity_sha256`, `gate_evaluation_id`, `gate_input_fingerprint_sha256`, `bridge_input_fingerprint_sha256`, `f2_contract_version`, `gate_version`, `rb2_policy_version`, `policy_version`, `policy_reference_sha256`, `as_of_utc`, `patient_id`, `doctor_id`, `lineage_label_policy`, `dr006_policy`, `item_count`, `evidence_link_count`, `exclusion_count` each equal the freshly recomputed or re-read value.
2. **Semantic output rows:** re-deriving the output identity from the **persisted rows themselves** (items ordered by `display_order`, each with its links ordered by `(kind, observation_id, document_id, page_index, char_start, char_end)`) yields exactly the stored `output_identity_sha256`; and that value equals the identity computed at T14 from this invocation's evaluator result.
3. **Links:** the persisted link set equals the set this invocation would write — same cardinality, same kinds, same referenced stored rows, no extras, no omissions.
4. **Exclusions:** the persisted `exclusion_count` equals `len(L3)` recomputed now, and the L1 set still equals F2's cached `history_exclusions`.
5. **Audit identity and content:** the row at `audit_event_id` exists and its `event_type`, `actor_type`, `actor_id`, `patient_id`, `workflow_run_id`, `subject_type`, `subject_id` and `outcome` match this invocation's expected values — the same eight comparisons G14 now enforces **structurally** (§6.4a condition 3), kept here as an independent application-layer safeguard — **and** its `safe_detail` still carries exactly the nine keys of `RB3_AUDIT_DETAIL_KEYS` in order (`fingerprint_version`, `evaluation_id`, `input`, `output`, `lineage_label_policy`, `dr006_policy`, `items`, `links`, `exclusions`), each equal to the freshly recomputed or re-read value, with `len(safe_detail) <= SAFE_DETAIL_MAX` and no truncation having occurred (§8.4). The `gate`, `bridge`, `policy` and `demo_only` values are validated from the sealed completion row in (1) above rather than from the audit string, which is why they are not duplicated there.

**Deterministic conflict precedence** — evaluated in this fixed order, the **first** match is reported, and every branch performs **zero writes**:

| Order | Reason | Condition |
|---|---|---|
| 1 | `completion_evidence_missing` | `review_item`/`evidence_link` rows exist for the run but no `review_evaluation` row does |
| 2 | `orphan_review_audit` | a review-persistence audit row exists for the run (found by recomputed key **and** by an `(event_type, workflow_run_id)` scan) but no completion row does — **including when the item/link set is empty** |
| 3 | `extra_persisted_items` | persisted items or links are not in the recomputed set |
| 4 | `missing_persisted_evidence` | recomputed items or links are absent from the persisted set |
| 5 | `input_identity_changed` | stored `input_fingerprint_sha256` ≠ recomputed, or any completion metadata mismatch in (1) above |
| 6 | `output_identity_changed` | stored `output_identity_sha256` ≠ recomputed from the persisted rows, or ≠ this invocation's T14 value |
| 7 | `audit_business_inconsistent` | the audit row's identity or `safe_detail` content fails validation (5) above |
| 8 | `audit_key_collision` | at T16 step 5 the helper returned a pre-existing row that is not this run's review-persistence audit |

All eight are reported as `409 E_IDEMPOTENCY_CONFLICT` with the reason string as a bounded detail. No repair, no append to a sealed result, no supersession, no second completion row, no second audit row — now structurally enforced by G15–G17 (run seals) **and G18–G25 (identity replacement guards)** as well as procedurally.

**The full case table:**

| # | Case | Behaviour |
|---|---|---|
| 1 | Exact same-run replay (all five validation groups pass) | **Zero writes of any kind.** Receipt: `replayed=True`, `evaluation_completed=True`, `review_items_persisted=0`, `review_items_total=item_count`, identities echoed from the stored completion record |
| 2 | Existing **extra** review items or links | precedence 3 `extra_persisted_items`; zero writes; no DELETE, no supersession (G2/G6 make removal impossible, G15/G16 seal the run, and G18–G23 refuse any replacement of an existing row) |
| 3 | **Missing** previously persisted items or links | precedence 4 `missing_persisted_evidence`; zero writes; no repair |
| 4 | Changed complete-history identity with **unchanged** candidate dedupe keys | precedence 5 `input_identity_changed` — per-row dedupe equality is explicitly **not** sufficient |
| 5 | Changed candidate set with **unchanged** F1 fingerprint | precedence 6 `output_identity_changed` |
| 6 | Original **zero-item** evaluation (including the T8a empty-selection path) | Completion row with `item_count=0`, `evidence_link_count=0`, `exclusion_count=len(L3)`, plus the single audit row; commit. Receipt: `evaluation_completed=True`, `review_items_persisted=0`, `review_items_total=0`, `replayed=False` |
| 7 | Repeated zero-item evaluation | case 1 semantics; `review_items_total=0` |
| 8 | Zero-item evaluation followed by new nonempty output | precedence 6 `output_identity_changed`; zero writes; no UPDATE, no second completion row, no append-to-old-result |
| 9 | Nonempty evaluation followed by zero output | precedence 6 `output_identity_changed`; zero writes |
| 10 | Existing audit row without a matching item/link set | precedence 2 `orphan_review_audit` when no completion row exists, else precedence 7 `audit_business_inconsistent`; **an orphan audit is never silently adopted**, even with zero items |
| 11 | Existing item/link set without the required completion evidence | precedence 1 `completion_evidence_missing`; rows whose originating evaluation cannot be proved are never adopted, extended or repaired |
| 12 | Concurrent invocation | The second writer blocks on `BEGIN IMMEDIATE`, then resolves as case 1 or by precedence; `ux_review_evaluation_run` + **G17/G24/G25** are the structural backstops → `IntegrityError` → rollback → conflict, never a partial write |
| 13 | Rollback and retry | A rolled-back attempt persisted nothing; the retry is a first evaluation. Equivalence is semantic; new UUIDs are expected and accepted |
| 14 | **Late insert, replacement or cross-run overwrite attempt** (any path: plain INSERT, `INSERT OR REPLACE`, `REPLACE INTO`, `INSERT OR IGNORE`, upsert `DO UPDATE`, upsert `DO NOTHING`; same run **or** a different run; before **or** after completion) | Refused structurally — post-completion by **G15/G16/G17**, and any attempt to delete-or-overwrite an existing row of any unique identity by **G18–G25** → `IntegrityError` → rollback → typed conflict; the existing rows **and** the completed evaluation's recorded counts are unchanged afterwards |
| 15 | **DR-006 present** | Denied at T12 **before** any replay comparison or write: `409 E_VALIDATION` reason `dr006_persistence_not_authorized` |

**One-evaluation-per-run invariant:** `UNIQUE (workflow_run_id)` + G12/G13 immutability + **G17 sealing, G24 primary-key protection and G25 unique-run replacement protection** mean a zero-item evaluation occupies the single slot exactly as a nonempty one does (cases 6–7), and any later differing evaluation is a typed conflict rather than a second record, an UPDATE or a supersession. Supersession remains reserved vocabulary requiring its own future owner authorization.

Uniqueness conflicts on `ux_review_dedupe`, `ux_review_order`, `ux_review_evaluation_run` or `ux_evidence_link_observation` are caught as `IntegrityError`, rolled back and reported as typed conflicts — never retried blindly.

### 8.3 Receipt semantics (`ReviewPersistenceReceiptV1`, proposed)

`contract_version='p4-rb3-receipt-1.0.0'`; run/patient/doctor ids; `as_of_utc`, `policy_version`, `policy_reference_sha256`; `gate_evaluation_id`, `gate_version`, both upstream fingerprints; `rb3_fingerprint_version`, `input_fingerprint_sha256`, `output_identity_sha256`; `evaluation_id`; `audit_event_id`; `lineage_label_policy`; `dr006_policy: Literal['prohibited_denied','not_present']` (a `'persisted'` value is **not** offered in this slice and would be added only by a future owner decision); and the honesty fields `evaluation_completed: Literal[True]`, `replayed: bool`, `review_items_persisted: int` (this invocation), `review_items_total: int`, `evidence_links_persisted: int`, `evidence_links_total: int`, `excluded_evidence: tuple[(observation_id, reason), ...]` (**L3**, the canonically deduplicated merge), `l1_exclusion_count: int`, `l2_exclusion_count: int`, `offline_evaluator_invoked: Literal[True]`, `runtime_evaluable: Literal[False]`, `policy_status: Literal['unapproved']`, `demo_only: Literal[True]`, `not_for_clinical_use: Literal[True]`.

**Zero-item receipts distinguish a completed durable evaluation from persisted review items:** `evaluation_completed=True` with `review_items_persisted=0` and `review_items_total=0` means "the evaluation ran, was proved and was recorded, and produced no items" — not "nothing happened" and not "the evaluator was skipped". RB3 uses its **own** field names and never reinterprets RB2's frozen result literals (`OfflineRuleResult.review_items_persisted=False` remains a statement about the offline evaluator, not about RB3's write).

### 8.4 Audit identity, request identity, insertion order and verification (**RB3-D05**, **RB3-R3-02**, **RB3-R4-06A**, **R4-S1**)

**Server-derived bounded audit request identity.** `append_audit_event` requires a keyword-only `request_id: str` with no default (`audit.py:110-124`), and `Principal` has no such attribute (`core/policies.py:32-50`). The only existing server request-id source, `request_id_for(request)` (`core/errors.py:213-229`), needs a Starlette `Request` and **honours a client-supplied `X-Request-ID` header** — unacceptable for a service with no HTTP surface and contrary to the prohibition on client-supplied tokens. RB3 therefore derives it internally from immutable persisted identifiers only:

```python
audit_request_identity = sha256(
    "|".join(("p4-rb3-audit-request", RB3_AUDIT_EVENT_TYPE, run.id, principal.user_id)).encode()
).hexdigest()      # 64 hex chars: within MAX_REQUEST_ID_LENGTH (core/errors.py:46) and the
                   # _is_identifier charset (:232-234); no client input, no wall clock
```

**Subject identity (R4-S1 correction).** `derive_audit_key`'s documented contract is "immutable facts of the request, **never a freshly generated row id**" (`audit.py:56-60`), and `AGENTS.md` §3.2 requires idempotency keys to derive "**only** from immutable, already-persisted identifiers … **never from a newly generated row ID**". Revision 3 passed the freshly generated `evaluation_id` as `subject_id`, violating both. Corrected: `subject_type='workflow_run'`, `subject_id=run.id`. The `evaluation_id` is recorded in the bounded `safe_detail` fragments and linked structurally by `review_evaluation.audit_event_id`. This also makes the audit key **stable across retries**, which is what makes orphan-audit detection deterministic.

One audit row per **first** completed evaluation, written inside the same transaction at T16 step 4 — **after** the item and link inserts and **before** the completion-row insert, because `review_evaluation.audit_event_id` is a NOT NULL FK and SQLite FKs are immediate:

```python
event = append_audit_event(
    db,
    event_type=RB3_AUDIT_EVENT_TYPE,          # "workflow.review.persisted"; additive literal —
                                              # event_type has no CHECK (models.py:399; DD §2.17)
    actor_type=principal.actor_type,          # existing derived property -> ActorType.USER for a
                                              # doctor (core/policies.py:47-50); no hard-coded enum,
                                              # and ActorType has no doctor member
    actor_id=principal.user_id,
    outcome=AuditOutcome.OK,
    request_id=audit_request_identity,        # server-derived above; never caller-supplied
    now=validation_clock,
    patient_id=run.patient_id,
    workflow_run_id=run.id,
    subject_type="workflow_run",              # immutable, already-persisted identifier
    subject_id=run.id,

```

**Exact audit detail fragments and the `SAFE_DETAIL_MAX = 500` length contract (RB3-R5-02).** `safe_detail()` joins non-empty stripped fragments with `"; "`, collapses whitespace and **truncates** to `SAFE_DETAIL_MAX = 500` (`audit.py:31`, `:77-87`), matching the `String(500)` column (`models.py:412`). The Revision-4 fragment set composed **529 characters** at the permitted maximum counts (`items=12`, `links=24`, `exclusions=200`) and **525** with single-digit counts, so the stored value was truncated and **`exclusions=…` and `demo_only=1` were lost** — which broke §8.2 (5)'s requirement that the audit row still carry the three counts, and made exact replay unable to satisfy its own stated audit-content validation. The helper and its 500-character contract are **not** changed; the fragment set is.

```python
    f"dr006_policy={dr006_policy}",                        # 'prohibited_denied'        -> 30 chars

    f"links={evidence_link_count}",                        # 0..24                       -> <= 8 chars

# worst case over the ENTIRE permitted domain: 330 payload chars + 8 separators x 2 = 346
# minimum (zero-item evaluation):                                                 = 342
```

**Why exactly these nine and not the Revision-4 thirteen.** Required by §8.2 (5) and preserved: `fingerprint_version`, `evaluation_id`, **both** RB3 semantic identity digests (`input`, `output`), `lineage_label_policy`, `dr006_policy` and **all three counts**. Removed as **redundant**, each already authoritatively stored in the sealed, immutable `review_evaluation` row that G14 structurally cross-checks and §8.2 (1) validates field by field: `gate=` → `gate_input_fingerprint_sha256`, `bridge=` → `bridge_input_fingerprint_sha256`, `policy=` → `policy_version` (itself CHECK-pinned and required to equal `workflow_run.policy_version`), `demo_only=1` → `review_evaluation.demo_only` (CHECK `= 1`). No shorter or less stable representation was needed once the redundancy was removed, so no abbreviation that would weaken readability is introduced. **Audit validation is not weakened:** every field §8.2 requires from the audit row is present, the four removed fields remain validated from a *stronger* source (a sealed, immutable, structurally cross-checked row rather than a truncated free-form string), and the removal is what makes the bound hold for **every** permitted invocation rather than only for small counts.

**Exact deterministic length assertion (required, not optional):**

```python
composed = safe_detail(*RB3_AUDIT_DETAIL_FRAGMENTS)
joined = "; ".join(f.strip() for f in RB3_AUDIT_DETAIL_FRAGMENTS if f and f.strip())
collapsed = " ".join(joined.split())                      # the helper's pre-truncation value
assert len(composed) <= SAFE_DETAIL_MAX                   # 346 <= 500 at the domain maximum
assert composed == collapsed                              # truncation never occurred
assert tuple(k.split("=", 1)[0] for k in composed.split("; ")) == RB3_AUDIT_DETAIL_KEYS
assert max(len(safe_detail(*f)) for f in every_permitted_count_combination) <= SAFE_DETAIL_MAX
```

The bound is proven over the **whole** permitted count domain (`items 0..12`, `links 0..24`, `exclusions 0..200`), measured maximum **346** (headroom **154**), so no invocation — including a zero-item evaluation and a maximum-exclusion evaluation — can depend on truncation. **Round-trip requirement:** after persistence and again during replay, the stored `safe_detail` is parsed by `dict(part.split("=", 1) for part in value.split("; "))` and every one of the nine keys must be present and equal to the freshly recomputed value; a missing or unequal key is precedence 7 `audit_business_inconsistent` with zero writes. Because keys are unique, ordered and whitespace-free, the parse is exact and needs no regular expression.

**No clinical prose, document text, `raw_text`, credential, token or free-text note** appears in any fragment (`REQ-AUDIT-02`), and no `User` identity column beyond `actor_id` is included.

**Validating the returned row (T16 step 5).** `append_audit_event` may return a **pre-existing** row matched by key alone, without comparing content (`:124-128`). RB3 reaching T16 means T15 found **no** completion record and **no** review-persistence audit for this run. A returned row whose `id`/`workflow_run_id`/`subject_id`/`safe_detail` identities do not match this invocation therefore cannot be a legitimate prior record of it — it indicates a key collision — and RB3 fails closed: `409 E_IDEMPOTENCY_CONFLICT`, reason `audit_key_collision`, rollback, zero writes. An unmatched pre-existing audit row is **never** adopted as completion evidence.

**Orphan-audit detection (T15, explicit).** Before branching, RB3 detects an existing review-persistence audit for the run by **both** (a) recomputing the key with the public `derive_audit_key` and selecting on `AuditEvent.idempotency_key`, and (b) scanning `select(AuditEvent).where(event_type == RB3_AUDIT_EVENT_TYPE, workflow_run_id == run.id)` (served by `ix_audit_run`, `models.py:395`). If any row is found while no `review_evaluation` row exists, the result is precedence 2 `orphan_review_audit` — **even when the item/link set is empty** — with zero writes and no adoption.

**Deferred-FK alternative, evaluated and rejected.** Deferring `review_evaluation.audit_event_id` would permit inserting the completion row first. Rejected because it changes connection-level pragma behaviour for the whole transaction rather than one insert; no existing migration declares a deferred constraint, so it would be a new, less-reviewed pattern; it makes the intermediate state transiently FK-invalid, observable by a concurrent reader or a crash between statements; and it is unnecessary — reordering two inserts achieves the same result with immediate constraints. The chosen order also lets G14 assert that the referenced audit row exists and matches.

**No committed denial audit:** `record_denial` commits (`:170-190`) and is prohibited. Audit/business-row consistency is structural as well as procedural: G14 requires the counts to equal the actual rows and the audit row to exist and match; `ux_review_evaluation_run` + G17 forbid a second or replaced completion row; G12/G13 make it immutable; G15/G16 forbid late child rows and G18–G25 forbid replacing any existing row of any of the three tables in any run — so the audit row, completion row and business rows are written together or not at all, and cannot afterwards be rewritten.
